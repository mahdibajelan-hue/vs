# ممیزی مرحلهٔ ۱ — توسعهٔ «کنترل اجرای پیمان‌های EPC» روی ماژول مدیریت اجرا

تاریخ: ۲۰۲۶‑۱۰‑۱۵ — فقط ممیزی؛ هیچ تغییری در کد یا دیتابیس این ماژول داده نشده است.

## ۱. معماری و فناوری فعلی
React 19 + TypeScript + Vite 8، zustand، Tailwind 4، recharts/chart.js، framer-motion، xlsx (ورود اکسل)، jspdf/html2canvas (PDF)، Supabase (Postgres + RLS + RPC SECURITY DEFINER + Edge Functions). یک حساب مشترک برای همهٔ ماژول‌ها؛ هر ماژول پوستهٔ خودش را دارد (`src/modules/*`) و دسترسی با `rasta_*` و جدول نقش ماژول (برای اجرا: `ex_project_roles` + تابع `ex_allows`) است. ماژول اجرا (`src/modules/execution`، جدول‌های `ex_*`، migrationها در `supabase/execution/001–009`) **از قبل وجود دارد** (۱۶ جدول، ۴۷۴۵ خط کد)؛ بنابراین کار پیش‌رو «توسعهٔ آن» است، نه ساخت ماژول جدید.

## ۵. تأمین داده برای داشبورد و موتور بهره‌وری
- **پیشرفت واقعی و برنامه‌ای:** از `ex_report_lines` (تأییدشده) و `ex_activities.planned_*`/`ex_baselines` — موجود.
- **نیرو/ماشین/ساعت:** `ex_report_resources` — نیازمند ستون یا جدول پیوند «اکیپ ↔ فعالیت».
- **شاخص‌های خط لوله (سرجوش، حفاری، لوله‌گذاری…):** با نگاشت `metric` در `ex_form_activity_map` از فرم‌ها به فعالیت‌ها؛ باید برای هر نوع فرم کامل شود.
- **شرایط/موانع:** `ex_report_stoppages` + آب‌وهوا + پیش‌نیازها (جدید).
- **کیفیت داده:** `completeness.ts` پایه است؛ برای اطمینان برآورد باید امتیاز کیفیت داده به آن اضافه شود.

## ۶. معماری پیشنهادی اتصال‌ها
- **برنامه‌ریزی:** جدول‌های جدید حداقلی `ex_schedule_import`, `ex_activity_deps`, `ex_lookahead_items`, `ex_commitments` (فعالیت = همان `ex_activities`)؛ ورود از Excel با الگوی `priceBookImport`؛ فایل اصلی در ذخیره‌سازی فایل موجود.
- **مهندسی:** بسته به تصمیم شما: ماژول سبک `eng_documents` یا فقط «پیش‌نیاز» نوع مدرک روی فعالیت.
- **تأمین:** `ex_links` (موجود) برای فعالیت ↔ `mtl_materials`/`mtl_package_items`؛ آمادگی از وضعیت واقعی `mtl_*` محاسبه شود.
- **Issue/Risk/Change:** استفاده از `ex_raise` و `ex_links`؛ افزودن `chg_change_requests`.
- **مالی:** پیوند `ex_report_lines`/ردیف فهرست‌بها ↔ ردیف `fin_payment_certificates` با چهار وضعیت مقدار (اجرایی، اندازه‌گیری‌شده، صورت‌وضعیت‌شده، پرداخت‌شده)؛ تأیید فنی ≠ استحقاق پرداخت.
- **موتور محاسباتی:** کتابخانهٔ خالص TypeScript آزمون‌پذیر `lib/productivity/*` (بدون AI)، با پارامترهای قابل تنظیم (بازهٔ میانگین، وزن‌دهی، حذف داده نامعتبر) و خروجی شامل فرضیات، دوره، بازهٔ عدم‌قطعیت.
- **دستیار:** یک Edge Function مشابه `im-ai` که فقط خروجی RPCهای مجاز و موتور را بازیابی/توضیح می‌دهد؛ محاسبه نمی‌کند.

## ۷. مراحل پیشنهادی پیاده‌سازی و آزمون
1. **گردش کار و گزارش روزانهٔ تکمیلی:** ستون‌های مستقل پیمانکار/مشاور/کارفرما، مرحلهٔ کارفرما قابل تنظیم، نسخه‌بندی، مدارک تصویری، فرم پیشنهادی.
2. **سربرگ و تحفظ:** لوگو/نام رسمی طرفین، سربرگ تاریخی، متن تحفظ قفل‌شده.
3. **تجمیع و نگاشت شاخص‌ها:** تکمیل `metric` و نمای تجمیعی خط/ایستگاه/تأسیسات.
4. **داشبورد صفحهٔ اصلی** (برنامه در برابر واقعی، چند پروژه، قابل‌پیمایش در زمان).
5. **اتصال مهندسی/تأمین و آمادگی فعالیت.**
6. **موتور بهره‌وری و پیش‌بینی** (آزمون با نمونه‌های عددی کنترل‌شده).
7. **سناریوهای جبرانی.**
8. **ورود برنامه، Lookahead، تعهدات.**
9. **اتصال Issue/Risk/Change و صورت‌وضعیت.**
10. **گزارش‌های دوره‌ای مدیریتی، هشدارها و دستیار هوشمند.**

هر مرحله: migration کنترل‌شده با برگشت‌پذیری، آزمون واحد، بررسی RLS هر نقش، گزارش موارد باقی‌مانده.

## ۸. تصمیم‌هایی که پیش از شروع لازم است
1. مرحلهٔ کارفرما به‌صورت پیش‌فرض خاموش باشد؟
2. متن تحفظ قراردادی و ارجاع حقوقی.
3. مدارک مهندسی: ماژول جدید سبک یا فقط پیش‌نیاز؟
4. فرمت‌های ورود برنامه: Excel، Primavera (XER/XLSX)، MS Project (XML)؟
5. ارائه‌دهندهٔ AI: دروازهٔ موجود (Gemini/OpenAI‑compatible) یا فقط OpenAI؟ و اجازهٔ ارسال چه دادهٔ پروژه‌ای به بیرون.
6. تعریف اکیپ و واحد بهره‌وری برای فعالیت‌های غیر از جوشکاری (اولویت‌بندی).
