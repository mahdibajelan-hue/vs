# Issue Management — وضعیت فعلی پیش از بازطراحی

> تاریخ بررسی: ۲۰۲۶-۱۰-۰۹ — پایگاه‌داده زنده: ۱۶ پروژه‌ی Issue، ۱۱۸ Issue، ۳۱ عضو، ۱۶ نگاشت تأییدشده به `master_projects`.
> منابع Issue موجود: `manual` و `mission_debrief`. ریسک (`rm_risks`): ۱۷۹، یافته‌های مأموریت: ۴۰، اقدامات `rasta_actions`: ۸۴.

## ۱. چه چیزی وجود دارد

| لایه | محتوا |
|---|---|
| دیتابیس | `im_projects` (فضای پروژه)، `im_project_members` (نقش‌های `admin/pursuer/approver`)، `im_issues` (عنوان، شرح، مسئول انجام، مسئول تأیید، اولویت ۴سطحی، مهلت به روز، وضعیت ۵حالته، منبع، `related_action_id`) |
| امنیت | RLS مبتنی بر عضویت (`im_is_project_member`)، دید پورتفولیویی از مسیر نگاشت `rasta_project_mappings` + `rasta_scope_ok_for_source`، تریگر `enforce_issue_approval_transition` (تفکیک مسئول انجام/تأیید) |
| یکپارچگی | `ms_transfer_finding` (یافته بازدید → Issue/Risk/Action)، `rasta_convert_action_to_issue` (اقدام معوق برج کنترل → Issue)، Deep-link از مأموریت‌ها، زنگ اعلان `my_notifications()` |
| رابط | داشبورد، پروژه‌ها، فهرست مشکلات (کارت)، گزارش تأخیر، «تحلیل سه‌سطحی» (Portfolio/Program/Project)، درباره ما؛ هویت بصری مستقل `issues.css` (تیره، کهربایی) |

## ۲. محدودیت‌ها نسبت به مأموریت جدید

- مدل داده تخت است: بدون شناسه یکتای خوانا، دسته‌بندی، شدت/فوریت جدا از اولویت، اثر (زمان/هزینه/کیفیت/ایمنی/قرارداد)، محل، حوزه تخصصی، مالک/مسئول پیگیری.
- «اقدام» (Task) وجود ندارد؛ فقط یک Issue با یک مسئول. نه Subtask، نه وابستگی، نه تمدید کنترل‌شده، نه توقف/Blocked.
- گردش کار ثابت ۵حالته؛ «اقدام انجام شد» از «مسئله واقعاً رفع شد» جدا نیست؛ معیار پذیرش/شواهد/علت ریشه‌ای/CAPA/درس‌آموخته/بازگشایی وجود ندارد.
- تاریخچه: فقط `updated_at`؛ تغییر مسئول/وضعیت/مهلت و دلیل آن ثبت نمی‌شود (Audit Trail ندارد).
- Decision Management، Issue مادر (Corporate)، تشخیص تکراری، پیوست، SLA، قالب، فیلتر ذخیره‌شده، ورود/خروج انبوه، اعلان چندکاناله و تشدید، هوش مصنوعی و پایگاه دانش: وجود ندارد.
- گزارش‌ها: فقط تأخیر و نرخ به‌موقع؛ KPIهای تعریف‌شده (Aging، Reopen Rate، Decision Lead Time …) ندارد.

## ۳. اصل‌های حاکم بر بازطراحی

1. **همان معماری**: `im_issues` در جا گسترش می‌یابد؛ جدول موازی ساخته نمی‌شود. ستون `status` (۵ مقدار) به‌عنوان وضعیت درشت برای کدهای موجود (تریگر تأیید، زنگ اعلان، مأموریت‌ها، برج کنترل) حفظ می‌شود و ستون جدید `stage` مرحله‌ی ریز گردش کار است؛ نگاشت `stage → status` را تریگر نگه می‌دارد.
2. **همه تغییرات additive و قابل بازگشت** (`add column if not exists`، بدون حذف داده).
3. **زیرساخت موجود**: کاربران = `profiles`، پروژه‌ها = `im_projects` ↔ `master_projects` (نگاشت)، دسترسی = `rasta_*`، اعلان = `my_notifications()`، هوش مصنوعی = الگوی ارائه‌دهنده‌ی مستقل `mission-ai`.
4. **سمت سرور محور**: انتقال مرحله، بستن، تمدید و ورود از منبع بیرونی فقط با RPC/تریگر اعتبارسنجی می‌شود.
